这次我给你定一个最终版：书为主、课程为辅、全程只做一个大项目，不再做一堆小实验
而且网络只学到 Linux Server 真正需要的深度，不把你带去实现 TCP 协议栈。

你的目标不是“学 Linux”，而是到寒假前形成一个明确画像：
> C++ / Linux Server / 并发 / Performance

最终主项目固定为：
> C++20 高性能异步 RPC Runtime + KV Service

KV 只是 workload，真正要展示的是 Server Runtime 和性能工程。
## 一、资源就这几个

| 定位资源怎么用     |                                                 |
| 网络快速补齐       | Beej's Guide to Network Programming             | 前期集中读，约一周
| Linux 机制参考    | TLPI《Linux/UNIX 系统编程手册》                    | 不通读，项目需要什么查什么 
| Server 架构参考   | 陈硕《Linux 多线程服务端编程》                      | 只读 Reactor / EventLoop / 多线程 Server 部分 
| 主书              |Brendan Gregg《性能之巅》第2版                     | 项目中后期认真读
| 课程补充          | MIT 6.1060 Software Performance Engineering     | 只补 performance 思维，不作为主线

Beej 现在仍在持续维护，所以网络入口不会有“二十年前教材”的问题。
TLPI 虽然是 2010 年出版，但它是 Linux 系统接口的权威参考，而不是我们拿来线性学习的教材；
作者 Michael Kerrisk 长期维护 Linux man-pages。

真正值得你**完整深入读**的是《Systems Performance 2nd Edition》。
它覆盖应用、CPU、内存、网络、benchmark、`perf`、Ftrace、BPF，而且第二版特意更新了 Linux/cloud/BPF 相关内容。
MIT 6.1060 则是性能工程的补充，
它 2026 年春季仍然开设，课程本身就是 project-based 的高性能、可扩展软件开发，
包含 cache/memory hierarchy、parallelism、profiling 等。
陈硕那本书年代比较老，所以**不当技术现状教材**。只拿它看一个今天仍然有价值的问题：`one loop per thread`、EventLoop、Connection ownership 这种 Server 架构是怎样组织起来的。作者自己对书的定位也正是 Linux 多线程 TCP Server 的这一套模型。

# 第 3～4 周：项目真正进入 Linux Server

现在学：
non-blocking socket
        ↓
epoll
        ↓
EventLoop
        ↓
Connection
        ↓
input/output Buffer

这时候 TLPI 只查这些对应机制，另外以最新 `man-pages` 为最终 API 依据。
项目内部开始形成：

Server
 │
 ├── Acceptor
 │
 └── EventLoop
       │
       ├── EpollPoller
       │
       └── Connection
              ├── InputBuffer
              └── OutputBuffer

这阶段最重要的不是 class 写漂亮，而是你必须真正解决：

> TCP 为什么一次可能读半条 RPC？
> 为什么一次 `read()` 也可能收到三条？
> 为什么 non-blocking `write()` 可能只写出去一部分？
> 为什么不能直接 `while(write())` 把线程卡死？
> 慢客户端为什么可能把 Server 内存撑爆？

到这里，一个靠谱 Linux Server 的“骨架”就出来了。

# 第 5～6 周：多核 Server

这时候再读陈硕关于：
> Reactor、EventLoop、one-loop-per-thread、多线程 Server 的对应部分。
然后项目变成：
                    Acceptor
                        │
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
      EventLoop 0   EventLoop 1   EventLoop 2
          │             │             │
     Connections   Connections   Connections

重点不是线程池 API。
而是：
> 一个 Connection 到底归谁所有？
> 一个 fd 能不能两个线程同时操作？
> 跨线程任务怎么通知 EventLoop？
> response 在另一个线程产生以后怎么回来？

这时候会自然用到：
thread
mutex
atomic
eventfd
task queue

你已经做过并发结构，所以这里没必要再上一整本 C++ concurrency。

# 第 7～8 周：把它真正做成 RPC Runtime

现在加入：
异步 Client
request_id
timeout
timer
pipelining
bounded queue
backpressure
graceful shutdown

这里才开始和网上常见的：
> “epoll + threadpool WebServer” 明显拉开。
例如同时：
Request 81
Request 82
Request 83

服务端执行完成的顺序可能：
82
81
83

Client 要靠 `request_id` 找到对应请求。
请求 81 已经 timeout，但是 response 又到了怎么办？
连接突然断掉，挂在这个连接上的 100 个 pending RPC 怎么处理？
Server 每秒只能处理 20 万请求，客户端每秒灌 100 万进来怎么办？
这些就是真正的 Server Runtime 问题。

## 这里才允许你开始“秀技术”
比如你发现：

8 thread
吞吐只比 4 thread 高 5%
P99 却翻倍

先别猜。查。
最后如果证明是：
共享 KV mutex
那么：
一个全局 HashMap + mutex
        ↓
16-way sharding
        ↓
重新 benchmark

如果发现：
malloc/free 占了很多 CPU
再研究 object pool。

如果发现：
大量 memcpy
再研究 scatter/gather I/O 或 buffer ownership。

如果发现：
跨线程 wakeup 很贵
再改线程模型。

高级技术只能由 profiler 逼出来。
这是这个项目与普通“手搓服务器”最大的区别。

# 四、到最后简历上真正应该有什么

不是：
> 熟悉 epoll、Reactor、多线程、io_uring。

而应该出现这种证据链：
设计并实现基于 non-blocking I/O + epoll 的
C++20 异步 RPC runtime；
实现 multi-reactor、多连接管理、RPC timeout、
backpressure 和异步 request/response；

构建完整 benchmark，
测量 QPS/P50/P95/P99；
使用 perf 定位 XX 瓶颈，
通过 XX 设计将 XXX 从 A 改善至 B；
实现 io_uring backend，
在相同 workload 下与 epoll 对照分析。
A/B 必须是真数据。
这才是现在这个环境里一个个人 Systems 项目应该达到的完成度。

所以最终你不需要同时上四门课。
