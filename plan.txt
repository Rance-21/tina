Phase 2：Workspace
Phase 2：文件树与代码编辑







wccftech.com

具体任务：

这里要确定几个技术细节：

项目管理：

不要让客户端随意传入绝对路径。

Server 维护项目登记表：
project_id: 1
name: tina
root: /home/user/projects/tina


客户端只传 project_id 和相对路径。

文件保存：

客户端读取文件时，Server 同时返回文件版本标识。

保存时客户端带上原来的版本标识。如果文件已经被 Agent 或其他程序修改，Server 返回冲突，而不是覆盖新内容。

文件缓存：

先不做复杂缓存，只缓存最近打开的文件和目录元数据。

使用 inotify 监听文件变化，后续再优化缓存失效。

前端：
- 文件树：普通树形组件。
- 编辑器：CodeMirror 6。
- 代码高亮：先支持 C++、Rust、CMake。
- 标签页：支持多个文件。
- 保存状态：显示已保存、未保存、冲突。
验收标准：

你可以躺在床上，用平板打开 Tina 的 server.cppm，修改几行代码，保存后 Fedora 上的文件确实改变。

这就是第一个真正的产品里程碑。

Phase 3：Terminal
Phase 3：远程终端







devpress.csdn.net


这一步是 Linux 系统编程含量很高的部分。

你提出的 cargo build、git commit 等操作，主要就通过这里完成。

Server 需要管理：
- PTY（伪终端）。
- Shell 子进程。
- 输入输出。
- 终端大小。
- 进程退出。
- 多个终端会话。
例如：
Terminal 1:
    cd ~/projects/tina
    cmake --build build

Terminal 2:
    cargo build

Terminal 3:
    git status


客户端使用 xterm.js 显示终端。

Server 使用 Linux PTY 接口创建终端进程，并通过事件推送输出。

这里有一个重要设计：

客户端断线不等于终端退出。

Terminal Session 应该由 Server 独立管理。平板断线之后，Shell 仍然运行，重新连接时可以重新 Attach。

第一版保证 Server 进程仍在运行时可以恢复终端。Server 自身崩溃后的终端恢复先不承诺，后续可以研究 tmux 或独立进程管理器。

验收标准：

你可以在平板上执行：
cd ~/projects/tina
cmake --build build
ctest --test-dir build


即使关闭平板网络，编译也能继续。

Phase 5：Agent
Phase 5：接入 Codex 和 Antigravity







hi-loop.com


这一步会让产品真正变得有意思。

先做 Agent Manager：
Agent Manager
    │
    ├── Codex Adapter
    │
    └── Antigravity Adapter


每个 Adapter 负责：
1. 启动 Agent 进程。
2. 管理标准输入输出。
3. 解析 Agent 事件。
4. 转换为 Tina 统一事件。
5. 管理会话。
6. 处理取消与错误。
开发顺序：
顺序	功能
1	启动 Codex
2	平板发送 Prompt
3	实时接收输出
4	显示任务状态
5	显示文件修改
6	审批危险操作
7	取消任务
8	接入 Antigravity

我建议第一版只接 Codex，完成稳定的交互后再接 Antigravity。

特别注意：不要把普通终端里的 ANSI 彩色输出直接当成 Agent 对话。优先使用 Agent 提供的结构化接口；如果只能使用交互式 TUI，就应该在 xterm.js 中展示，而不是强行解析成聊天消息。

还有，Agent 不应该在 Fedora 每次启动时全部自动运行，而是由用户选择后按需启动。

验收标准：

你能够躺在床上，通过平板让 Codex 修改 Tina，查看它的执行过程，查看 Git Diff，再决定是否提交。

Phase 6：Storage 与可靠性
Phase 6：让 Tina 真正可靠
这部分不需要自研数据库。

我建议采用：
数据	保存方式
项目配置	SQLite
设备认证信息	SQLite + 安全存储
Terminal 会话元数据	SQLite
Agent 会话元数据	SQLite
Agent 任务历史	SQLite
文件内容	原有 Linux 文件系统
终端输出历史	有界内存缓冲区 + 可选日志文件
热点文件	内存缓存

具体任务：
1. 引入 SQLite。
2. 保存项目配置。
3. 保存终端和 Agent 会话信息。
4. 保存最近任务历史。
5. 实现文件版本检测。
6. 实现缓存失效。
7. 实现日志轮转。
8. 实现 Server 重启后的状态恢复。
这里需要区分两种恢复：
- 元数据恢复：知道之前有哪些项目、任务和会话。
- 进程恢复：之前的 Shell 或 Agent 进程是否还活着。
两者不是一回事。SQLite 只能恢复前者，后者需要额外的进程管理设计。

验收标准：

Server 重启后，项目配置、历史任务和会话记录仍然存在；已经丢失的进程会被明确标记，而不是假装仍然运行。

Phase 7：Performance
Phase 7：性能工程——整个项目最重要的研究阶段
实际上，这一阶段从 Phase 1 就应该开始积累数据，而不是等所有功能完成才开始。

我建议最后集中完成以下实验。
实验	主要指标	优化对象
RPC 请求压力	QPS、P99、CPU	EventLoop、WorkerPool
大量文件树扫描	延迟、系统调用数	文件扫描、缓存
多文件并发读取	吞吐、P99、RSS	文件 I/O、内存
终端持续输出	首字节延迟、缓冲区	网络发送、背压
Agent 高频事件	排队时间、CPU	事件分发
多任务混合负载	交互延迟、队列长度	调度、公平性

尤其要做一个重要的实验：

在 Fedora 上执行大型 cargo build，同时让平板进行文件浏览、编辑和终端交互。

比较不同 WorkerPool、队列策略、缓存策略下的交互延迟。

这比单纯测一个 QPS 数字更有价值。

使用的工具：
- perf：CPU 热点、缓存失效。
- heaptrack：内存分配。
- strace：系统调用。
- iostat：磁盘 I/O。
- 自己写的 Python 压测驱动：并发请求、延迟统计。
- Tina 内部 Metrics：队列长度、处理时间、内存占用。
最终形成一份 Benchmark 文档，记录优化前后的真实数据。

五、每个阶段的性能研究安排
为了防止最后又变成「功能写了一大堆，性能没研究」，我专门把每个阶段需要留下的性能成果列出来。
阶段	必须记录的性能数据
RPC	请求延迟、吞吐、CPU
Workspace	目录扫描时间、文件读取延迟
Terminal	输入响应、输出吞吐、内存占用
Git	Status / Diff 延迟
Agent	事件延迟、缓冲区占用
Storage	SQLite 查询、缓存命中、恢复时间
综合	混合负载下 P99、CPU、RSS

不要每个阶段都为了优化而优化。

先测量，找到真正的瓶颈，再决定是否改代码。

七、现在具体应该做什么？
我不建议你马上开始写 Tauri 的界面，也不建议直接改 server.cppm。

我们按下面的顺序开始。
当前任务
Phase 0：总体架构设计
先完成三件事：
1. 明确 Server 内部的模块关系，尤其是 RPC Router 如何管理 Workspace、Terminal、Git、Agent。
2. 明确 Android、Tauri Rust Backend 和 C++ Server 的通信关系。
3. 明确协议中的 Request、Response、Event，以及各模块的消息格式。
暂时不写业务代码，不创建一大堆空模块。

完成后再进入 Phase 1，先打通 Android 和 Fedora。

我建议以后每个阶段都采用同样的开发方式：
1. 先解释这个阶段要解决的问题。
2. 设计模块和接口。
3. 一次实现一到两个文件。
4. 结合你的现有代码讲清楚原理。
5. 编译、测试、提交 Git。
6. 记录性能数据和技术笔记。
你不需要一开始就懂整个框架。我们会随着功能增加逐渐建立它。

最重要的一点：Tina 的目标不是成为一个功能齐全的 VS Code，而是成为一个你真正愿意每天使用的远程开发工具，同时让你在实现它的过程中深入掌握 C++、Linux、并发、存储和性能工程。

这次路线就以此为准。
